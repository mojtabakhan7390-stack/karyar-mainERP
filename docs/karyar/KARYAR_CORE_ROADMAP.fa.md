# ۱. معماری Core در یک تصویر

Karyar در سه لایه ساخته می‌شود:

<pre class="ltr">
┌──────────────────────────────────────────────────────────┐
│ Customer Pack  (YAML files in GitHub)                    │  ← different per customer
│ agents, processes, approval rules, templates             │  ← the only thing AI Builder edits
├──────────────────────────────────────────────────────────┤
│ Karyar Core  (one Frappe app: karyar)                    │  ← same for everyone
│ agent engine, Task, Approval, Permission, Promote,       │  ← only developers (Claude Code) change it
│ Idempotency, Pack loader, n8n generator                  │
├──────────────────────────────────────────────────────────┤
│ ERPNext  (business logic + business data)                │  ← untouched
└──────────────────────────────────────────────────────────┘
n8n ← runs the processes that Core generates from the Pack
</pre>

**قاعده طلایی:** Core «موتور» است و Pack «تنظیمات».

اگر برای مشتری جدید مجبور شدید کد Core را تغییر دهید، یکی از این دو حالت است:

- یک **قابلیت عمومی** کم بوده که باید به Core اضافه شود و همه مشتری‌ها از آن سود می‌برند.
- یا **مسیر اشتباه** است.

> **وضعیت فعلی:** نمونه‌های فعلی (هانا، آوا، پنل‌ها، ثبت لید) کاملاً داخل n8n ساخته شده‌اند. منطق کسب‌وکار، دیتابیس Postgres با جدول‌های `karyar_*`، و مجوز با کد ورود همه در n8n است. این برای نمونه اولیه درست بوده، ولی همان الگویی است که Core جایگزینش می‌کند. **فعلاً به آن‌ها دست نمی‌زنیم** و از آن‌ها فقط به‌عنوان نیازمندی‌های اولین مشتری استفاده می‌کنیم.

# ۲. چه چیزی ثابت است و چه چیزی تغییر می‌کند

| ثابت (Core، کد) | قابل‌تغییر (Pack، فایل تنظیمات) |
|---|---|
| انواع گام فرایند: `agent_task`، `human_task`، `approval`، `promote`، `notify`، `integration`، `condition` | **فرایندها:** کدام گام‌ها، با چه ترتیبی، با چه شرطی |
| ابزارهای ایجنت (Tools)، مثل «ساخت Lead» و «خواندن گزارش» | **کدام ابزارها** به کدام ایجنت داده شوند |
| موتور ایجنت، اتصال به مدل AI، ثبت مصرف | **ایجنت‌ها:** نام، شخصیت، دستورالعمل، مدل، کانال |
| Human Task، Change Proposal، موتور Approval | **قوانین تأیید:** چه کسی، چند نفر، با چه ترتیبی |
| Permission، Promote، Idempotency، Audit | **نقش‌ها** و انتساب افراد و ایجنت‌ها به نقش‌ها |
| بارگذار Pack و اعتبارسنج آن (Validator) | فیلدهای اضافه ERPNext، Templateهای Human Task، گزارش‌های مجاز |
| تولیدکننده Workflow برای n8n | متن پیام‌ها، سقف‌ها، و مدت نگهداری داده |

# ۳. نگهداری Workflowها

## ۳.۱ مقایسه روش‌ها

| روش | مشکل اگر به‌تنهایی استفاده شود |
|---|---|
| فقط کد (Python) | AI نمی‌تواند بی‌خطر تغییرش دهد. هر مشتری به برنامه‌نویس نیاز دارد |
| فقط دیتابیس (فرم‌ها) | بدون نسخه، تاریخچه، بازبینی و امکان بازگشت |
| فقط JSON ‏n8n | بزرگ و شکننده. AI در ویرایش آن خطا می‌کند و منطق پراکنده می‌شود |
| **✅ فایل YAML در Git، به‌عنوان منبع حقیقت** | خوانا برای انسان و AI، نسخه‌دار، قابل بازبینی و قابل اعتبارسنجی |

## ۳.۲ مسیر

<pre class="ltr">
YAML in GitHub (source of truth)
  → Validator checks it
  → apply-pack loads it into the Karyar database (runtime copy)
  → generator builds and publishes the n8n workflows from it
</pre>

## ۳.۳ نمونه یک فرایند در Pack

<pre class="ltr">
process: clinic_intake
version: 3
trigger: intake.completed
steps:
  - id: review
    type: human_task
    template: staff_review
    assignee: responsibility:reception
  - id: register
    type: promote
    operation: crm.lead
    approval: none
  - id: handoff
    type: agent_task
    responsibility: sales      # currently assigned to Hanna; the name never appears here
</pre>

> ⚠️ **اصلاح پیشنهادی نسبت به سند معماری ۱٫۱ (CR-06):** در سند فعلی آمده «Workflowها در ویرایشگر n8n ساخته می‌شوند». برای اینکه AI Builder بتواند Workflow بسازد، پیشنهاد می‌شود **منبع حقیقت YAML باشد و n8n از روی آن تولید شود.** n8n همچنان مجری است و این تغییر با بقیه معماری تناقض ندارد. **نیاز به تأیید دارد.**

# ۴. نقش هر جزء

| جزء | نقش |
|---|---|
| **ERPNext** | ثبت، محاسبه و اعتبارسنجی کسب‌وکار. منبع حقیقت داده |
| **Karyar Core** | موتور: ایجنت‌ها، Task، Approval، Permission، Promote، بارگذار Pack، تولیدکننده n8n |
| **n8n** | اجرای فرایندهایی که Core ساخته، و اتصال به سرویس‌های بیرونی (پیامک، APIها) |
| **ایجنت‌های Runtime** (آوا، هانا و…) | داخل Core، با ابزارهای مجاز، روی داده واقعی کار می‌کنند |
| **Workflow Builder** | **فقط Pack را تغییر می‌دهد.** به کد Core و داده مشتری دسترسی ندارد |

# ۵. Workflow Builder چطور کار کند

Builder مثل یک کارمند تازه‌وارد دقیق است که فقط حق پیشنهاد دارد:

1. **شما توضیح می‌دهید:** «فرایند فروش این مشتری این‌طور باشد…»
2. **Builder پیشنهاد می‌دهد:** فقط فایل‌های YAML همان Pack را تغییر می‌دهد و نتیجه را به‌شکل یک **Pull Request** با توضیح فارسی تحویل می‌دهد.
3. **بررسی خودکار (Validator)** پیش از اینکه شما چیزی ببینید:
   - هیچ ابزار، نقش یا Template ناموجودی به کار نرفته باشد.
   - هر `promote` قانون تأیید یا Policy اجرای خودکار داشته باشد.
   - هیچ ایجنتی بیش از اختیارش ابزار نگرفته باشد.
4. **شبیه‌سازی:** چند سناریوی آزمایشی (مثلاً «مشتری اطلاعاتش را کامل نداد») روی محیط تست اجرا می‌شود.
5. **شما تأیید می‌کنید (Merge)** و Pack روی آن مشتری اعمال می‌شود.
6. **اگر قابلیتی در Core نباشد**، Builder آن را خودش نمی‌سازد. یک Issue باز می‌کند: «برای این کار به ابزار X نیاز است».

- **نسخه اول Builder همان Claude Code است**، همراه با یک دستورالعمل اختصاصی (Skill) برای ویرایش Pack.
- **Builder درون محصول** (با رابط گفت‌وگو) مرحله بعد است.

# ۶. نقش GitHub و Claude Code

| | نقش |
|---|---|
| **GitHub** | منبع حقیقت همه‌چیز. مخزن `karyar` (اپ Core) و مخزن `karyar-packs` (برای هر مشتری یک پوشه). هر تغییر از طریق PR انجام می‌شود و تست‌ها خودکار اجرا می‌شوند |
| **Claude Code** | (۱) **سازنده Core:** شما مشخصات را به فارسی می‌نویسید و Claude Code کد و تست را می‌نویسد و PR می‌دهد. (۲) **نسخه اول Workflow Builder** |
| **شما (معمار)** | نوشتن مشخصات در قالب Issue، بررسی توضیح PR و نتیجه تست‌ها، و Merge. **خواندن کد لازم نیست** |
| **`CLAUDE.md`** | مهم‌ترین فایل پروژه. قوانین معماری نسخه ۱٫۱ به‌صورت دستور در آن نوشته می‌شود (مثلاً «هرگز SQL ننویس»، «هر promote باید Idempotency داشته باشد»). Claude Code هر بار آن را می‌خواند |

**چرخه کاری شما در هر مرحله:**

1. یک Issue با توضیح فارسی بنویسید: «چه می‌خواهم» و «چطور بفهمم درست کار می‌کند».
2. از Claude Code بخواهید آن Issue را پیاده کند و PR بدهد.
3. توضیح PR و نتیجه تست‌ها را بخوانید. اگر چیزی مبهم بود، از خود Claude Code بپرسید.
4. اگر «علامت تمام شدن» آن مرحله برقرار بود، Merge کنید.

# ۷. MVP: چه بسازیم و چه نسازیم

**می‌سازیم:**

- فرمت Pack و Validator آن، به‌همراه یک Pack نمونه
- اپ `karyar` با DocTypeهای اصلی: Agent، Case، Human Task، Approval، Audit، Idempotency
- موتور ایجنت با ۳ تا ۵ ابزار و یک مدل AI
- Human Task، Change Proposal، و Approval (تک‌نفره و M از N)
- Promote برای Lead و Sales Order، با Idempotency
- انتشار رویداد و تولیدکننده n8n برای ۴ نوع گام: `human_task`، `agent_task`، `promote`، `notify`
- صفحه ساده گفت‌وگو و Task (حتی داخل Desk خود Frappe)

**نمی‌سازیم:**

- UI زیبا
- Builder گرافیکی
- چند کانال همزمان (فقط یک کانال)
- RPA، سامانه مودیان، حقوق و دستمزد
- صورت‌حساب‌دهی و Control Plane
- صوت و MCP
- انتقال سیستم‌های فعلی n8n

# ۸. ساختار Pack برای هر مشتری

<pre class="ltr">
karyar-packs/
├── _base/                 shared by everyone (base roles, generic templates)
├── clinic/                industry pack: clinics
├── hana-badahang/         this customer's pack (only its differences from _base)
│   ├── pack.yaml          name, version, which pack it inherits from
│   ├── agents/  processes/  approvals/  templates/  erp_fields/
│   └── tests/             test scenarios for this customer
</pre>

- **مشتری جدید یعنی یک پوشه جدید.** از `_base` یا Pack صنفی ارث می‌برد و فقط تفاوت‌هایش را اضافه می‌کند.
- **هانا بداهنگ اولین مشتری روی Core است.** Workflowهای فعلی او در n8n فقط **مرجع نیازمندی‌ها** هستند. نسخه جدید روی Core ساخته می‌شود و نسخه فعلی تا آماده شدن آن کار می‌کند.
- **دوباره‌کاری نمی‌شود:** منطق یک‌بار درست ساخته می‌شود و برای مشتری بعدی هم قابل استفاده است.

# ۱۰. شروع از همین هفته

**از «قرارداد» شروع کنید، نه از کد اپ.**

1. **امروز:** در GitHub دو مخزن خالی بسازید: `karyar` و `karyar-packs`.
2. **روز اول با Claude Code:** «سند `docs/karyar/KARYAR_ARCHITECTURE.fa.md` را بخوان و یک `CLAUDE.md` برای مخزن `karyar` بنویس که همه قوانین آن را به‌صورت دستور شامل شود.» خروجی را بخوانید تا مطمئن شوید قوانین درست فهمیده شده‌اند.
3. **بقیه هفته: مرحله ۱ (فرمت Pack و Validator).** چرا اول این؟
   - به ERPNext و سرور نیاز ندارد، پس سریع و کم‌دردسر است.
   - همه مراحل بعدی (اپ، n8n، Builder) روی آن سوار می‌شوند.
   - **کار اصلی شما در آن است:** توضیح فرایند به زبان ساده. Claude Code آن را به YAML و Validator تبدیل می‌کند.
4. **بعد** مراحل ۲ تا ۱۰ را به ترتیب جدول جلو ببرید. هر مرحله یک PR است.
