# CR-01 — Workflow در فاز اول با n8n

## تصمیم

در فاز اول، Workflow Engine اختصاصی در Karyar ساخته **نمی‌شود**. n8n خودمیزبان محل ساخت و اجرای Workflowها و Automationهاست.

- **Karyar:** ایجنت‌ها، منطق کسب‌وکار، ERPNext، داده، مجوز و APIها
- **n8n:** ترتیب گام‌ها، مسیریابی بین ایجنت‌ها، triggerها، اعلان‌ها و اتصال به سرویس‌های بیرونی

**اصل راهنما:** «n8n ترتیب کارها را تعیین می‌کند؛ Karyar تصمیم می‌گیرد و اجرا می‌کند.»

**دلیل:** تیم و زیرساخت ساخت موتور اختصاصی فعلاً وجود ندارد. n8n آشناست، خودمیزبان اجرا می‌شود و رسیدن به اولین مشتری را سریع‌تر می‌کند. اگر بعداً لازم شد، منطق به موتور داخلی منتقل می‌شود.

## محل ساخت و نگهداری Workflowها

- **ساخت و اجرا:** در n8n خودمیزبان، با دو نمونه جدا برای test و production.
- **نسخه‌داری:** export به JSON در `karyar-deploy/n8n/workflows/`. اعتبارنامه‌ها در git ذخیره نمی‌شوند.
- **مستندسازی:** کنار هر Workflow یک `README` با Trigger، گام‌ها و endpointهای Karyar که صدا زده می‌شوند. این فایل‌ها پایه انتقال آینده‌اند.
- **نام‌گذاری:** `KY | <process> | <segment>`

## قواعد سخت n8n

1. n8n **فقط** با Karyar API v1 کار می‌کند. نوشتن یا خواندن مستقیم از ERPNext (نود ERPNext یا `/api/resource`) و دسترسی به پایگاه داده ممنوع است.
2. **منطق کسب‌وکار در Code Node ممنوع است.** Code Node فقط برای نگاشت و قالب‌بندی داده است.
3. n8n روی **پرچم‌هایی که Karyar برمی‌گرداند** شرط می‌گذارد (مثلاً `requires_approval`). خودش محاسبه کسب‌وکاری انجام نمی‌دهد.
4. نودهای AI Agent در n8n به‌جای ایجنت‌های Karyar استفاده نمی‌شوند.
5. **Workflowها کوتاه و زنجیره‌ای‌اند.** Wait چندروزه برای انتظار انسان ممنوع است. وضعیت پرونده در `Karyar Case` نگه داشته می‌شود.
6. n8n **Draft و داده کسب‌وکاری نگه نمی‌دارد.** فقط `case_id` و حداقل فیلدهای لازم منتقل می‌شوند. ذخیره داده اجراهای موفقِ جریان‌های حساس خاموش است و داده‌های اجرا به‌صورت خودکار حذف می‌شوند (pruning).
7. **`case_id` و `correlation_id` در همه فراخوانی‌ها منتقل می‌شوند.** شناسه execution در n8n روی Case ثبت می‌شود.
8. گفت‌وگوی زنده ایجنت با مشتری در Channel Gateway داخل Karyar می‌ماند. فقط **نتیجه** گفت‌وگو به n8n می‌رود. ⏳ *منتظر تأیید نهایی*

## اتصال

| جهت | سازوکار |
|---|---|
| Karyar ← n8n | رویدادهای ERPNext از DocType ‏Webhook خود Frappe (شرط‌گذاری، HMAC و لاگ). رویدادهای Karyar مثل `intake.completed`، `human_task.decided` و `agent.task.completed` با یک تابع کوچک `emit_event()` که بعد از commit اجرا می‌شود |
| n8n ← Karyar | نود HTTP Request به Karyar API v1 با کلید API کاربر `n8n@karyar` (دسترسی حداقلی). زیرWorkflow مشترک «Call Karyar» برای احراز هویت و خطاها |
| n8n و ایجنت‌ها | `agents.run_task` ناهمگام است. پایان کار ایجنت با رویداد `agent.task.completed` به n8n اعلام می‌شود |
| n8n و انسان | n8n با `human_tasks.create` کار انسانی را می‌سازد و Workflow تمام می‌شود. تصمیم انسان با رویداد `human_task.decided` مرحله بعد را شروع می‌کند |

**پاسخ سؤال‌های قبلی:**
- اعلان‌ها (پیامک، ایمیل، پیام اطلاع‌رسانی) از n8n ارسال می‌شوند.
- اعتبارنامه سرویس‌های بیرونی در n8n نگه داشته می‌شود.

## پیاده‌سازی در فاز اول

- **Karyar:**
  - DocTypeها: `Karyar Agent`، `Conversation`، `Message`، `Karyar Case`، `Human Task`، `Audit Log`، `AI Usage Log`، `Karyar Settings`
  - اجرای ساده ایجنت، و یک wrapper برای مدل AI که مصرف را ثبت می‌کند
  - ۸ تا ۱۵ ابزار پایلوت
  - ۸ تا ۱۰ endpoint در API v1، همه با `idempotency_key`
  - تابع `emit_event()` و Webhookهای Frappe
  - چت مشتری و Workspace حداقلی
  - نرمال‌سازی و اعتبارسنج‌های فارسی
  - قانون semgrep
- **n8n:**
  - Docker با Postgres در شبکه خصوصی
  - pruning داده‌های اجرا
  - زیرWorkflow «Call Karyar» و Error Workflow
  - ۳ تا ۵ Workflow پایلوت
  - اسکریپت export به git

## موکول‌شده به آینده

- Workflow Engine داخلی
- Automation Gateway، Action Contract، Adapter و Integration Job
- Outbox و Event Bus اختصاصی
- تأیید موازی «M از N» و escalation پیشرفته
- سازنده گرافیکی
- چندمستأجری n8n (برای مشتری اول یک n8n کافی است)
- RPA، مودیان، MCP، حافظه بلندمدت، مدیریت کامل هزینه، LiteLLM و Control Plane

## ریسک‌های ثبت‌شده

- تست و بازبینی منطق ترتیبی در n8n سخت‌تر است.
- Webhook خود Frappe در صورت شکست، خودکار retry نمی‌کند. راه کاهش: لاگ خطا، به‌علاوه یک Workflow زمان‌بندی‌شده که «پرونده‌های بی‌حرکت» را از Karyar می‌پرسد.
- عیب‌یابی بین دو سیستم سخت‌تر است. راه کاهش: `correlation_id` در همه فراخوانی‌ها.
- مجوز Sustainable Use در n8n قبل از فروش تجاری باید بررسی شود.

## CR-01a — جایگزین‌شده

پیشنهاد قبلی شامل Automation Gateway، Action Contract، Executor Binding، Adapterها و `Integration Job` در فاز اول اجرا **نمی‌شود**. جای آن را قواعد ۱ تا ۸ بالا می‌گیرند. این پیشنهاد به‌عنوان مسیر احتمالی آینده در §۳۰ ثبت می‌شود.

# CR-02 — مرز داده Karyar و ERPNext

## تصمیم

| دسته | چه چیزی | کجا | عمر |
|---|---|---|---|
| **Karyar Draft** | اطلاعات ناقص، پیش‌نویس، تغییرات پیشنهادی، داده در حال تکمیل | `Karyar Case.draft_data` و payload در `Human Task` | تا ثبت نهایی (Promote) یا رها شدن |
| **Conversation Context** | پیام‌ها و خلاصه تعامل | `Conversation` و `Message`، و فیلد `summary` | طبق سیاست نگهداری |
| **داده نهایی کسب‌وکار** | Lead، مشتری، سفارش، سند حسابداری و… | **ERPNext (Source of Truth)** | دائمی |
| **سوابق فرایند** (کمکی) | مرحله پرونده، ارجاع به اسناد ERPNext، تصمیم‌ها، ممیزی، مصرف AI | Karyar | دائمی |

**چرخه عمر:** گفت‌وگو ← Draft در Karyar ← (تأیید مشتری؟) ← (تأیید انسانی؟) ← **Promote** ← ERPNext.

پس از Promote، Case فقط **ارجاع** و snapshot ممیزی را نگه می‌دارد. دو تأیید داخل پرانتز اختیاری‌اند و برای هر Workflow قابل تنظیم‌اند.

## پاسخ‌های تأییدشده

1. **Draft اسناد مالی و پیچیده در Karyar می‌ماند.**
   - برای محاسباتی که متعلق به ERPNext است (مالیات، جمع‌ها، ثبت‌های دفتر کل)، فقط **پیش‌نمایش بدون ذخیره** از ERPNext گرفته می‌شود.
   - بعد از تأیید، سند نهایی در ERPNext ساخته و ثبت (Submit) می‌شود.
   - محاسبات ERPNext در Karyar بازنویسی **نمی‌شوند**.
2. **Draftهای ناقص و رهاشده** با مدت نگهداری **قابل تنظیم برای هر Workflow** مدیریت می‌شوند.
   - ۳۰ روز فقط **مقدار پیش‌فرض** است، نه قانون ثابت.
   - امکان ثبت «Lead ناقص» برای هر Workflow قابل تنظیم است و **پیش‌فرض آن خاموش** است.
3. **کف ایمنی تأیید در Karyar وجود دارد.**
   - اگر عملیاتی طبق Policy نیاز به تأیید داشته باشد، Karyar ثبت نهایی در ERPNext را **بدون تأیید معتبر رد می‌کند**.
   - این قاعده حتی وقتی Workflow در n8n گام تأیید را جا انداخته باشد اعمال می‌شود.

## قواعد (متن نهایی برای سند)

1. **Draft فقط «دلتا» نگه می‌دارد.** برای موجودیت‌هایی که در ERPNext وجود دارند، فقط ارجاع به‌علاوه اطلاعات جدید یا تغییرکرده ذخیره می‌شود. تغییرات اطلاعات پایه در گام Promote روی ERPNext اعمال می‌شوند.
2. **Promote یک endpoint واحد در Karyar است** که n8n صدا می‌زند. این endpoint به ترتیب:
   1. کامل بودن داده را طبق Schema بررسی می‌کند.
   2. سیاست تأیید را بررسی می‌کند (قاعده ۳).
   3. با `idempotency_key` در ERPNext ثبت می‌کند.
   4. ارجاع (`doctype`/`name`) را روی Case ذخیره می‌کند.
   5. Draft را «منتقل‌شده» علامت می‌زند و قفل می‌کند.
3. **سیاست تأیید (کف ایمنی):**
   - یک جدول ساده در `Karyar Settings` با ستون‌های: نوع عملیات، نیاز به تأیید، نقش تأییدکننده، سطح تأیید (`none`، `confirm` یا `strong`).
   - Promote وقتی موفق می‌شود که برای عملیات‌های فهرست‌شده یک **Human Task تأییدشده** وجود داشته باشد که `payload_hash` آن **دقیقاً با Draft فعلی یکی باشد**. در غیر این صورت درخواست رد می‌شود و رویداد `security.approval_missing` ثبت می‌شود.
   - عملیاتی که در این جدول نیست، بدون تأیید مجاز است.
   - اینکه Workflow گام تأیید داشته باشد یا نه، همچنان در n8n تعیین می‌شود. این جدول فقط **کف** را تعیین می‌کند.
4. **پیش‌نمایش ERPNext بدون ذخیره:**
   - سند ERPNext در حافظه ساخته می‌شود و محاسبات خود ERPNext روی آن اجرا می‌شود (مثل `calculate_taxes_and_totals`، و برای اسناد حسابداری `get_accounting_ledger_preview`). سپس نتیجه بدون ذخیره برگردانده می‌شود.
   - این پیش‌نمایش به تأییدکننده نمایش داده می‌شود و **hash آن بخشی از آن چیزی است که تأیید می‌شود.**
   - در زمان Promote، اگر محاسبه مجدد نتیجه متفاوتی بدهد (مثلاً نرخ یا موجودی تغییر کرده باشد)، Promote متوقف می‌شود و تأیید دوباره لازم است.
5. **بعد از Promote، ایجنت داده اصلی را فقط از ERPNext می‌خواند.** context ایجنت شامل ارجاع‌ها و مرحله از Case، به‌علاوه داده تازه با ابزارها از ERPNext است. Draft قفل‌شده و snapshot در دسترس ابزارهای ایجنت **نیستند**.
6. **اصلاح بعد از ثبت نهایی فقط روی ERPNext** انجام می‌شود، از طریق اقدام کسب‌وکاری Karyar. در صورت لغو و اصلاح سند (Amend)، Case به سند جدید ارجاع می‌دهد.
7. **snapshot تأییدشده فقط برای ممیزی** نگه داشته می‌شود. فقط‌خواندنی است و داده شخصی آن بعد از دوره نگهداری قابل پاک‌سازی است.
8. **خلاصه مکالمه** قصد، ترجیحات، سؤال‌های باز، قول‌های داده‌شده و لحن را نگه می‌دارد. واقعیت‌های کسب‌وکاری در خلاصه با برچسب «طبق گفته مشتری در تاریخ X» ثبت می‌شوند و ایجنت برای واقعیت‌ها **همیشه** از ERPNext استفاده می‌کند.
9. **سابقه مکالمات قبلی:** هر Conversation به Contact/Lead/Customer در ERPNext متصل است. ایجنت خلاصه چند مکالمه آخر **همان مخاطب** را می‌بیند. DocType جدیدی لازم نیست.
10. **Draft رهاشده:**
    - بعد از مدت نگهداری Workflow (پیش‌فرض ۳۰ روز)، Case با وضعیت `abandoned` بسته و داده شخصی Draft پاک می‌شود.
    - اگر گزینه «ثبت Lead ناقص» برای آن Workflow روشن باشد، **قبل از** پاک‌سازی، یک Lead با وضعیت «ناقص» در ERPNext ساخته می‌شود.
    - کف ایمنی تأیید برای این Lead هم اعمال می‌شود، اگر در Policy تعریف شده باشد.
11. **n8n هیچ‌وقت Draft نگه نمی‌دارد** (همان قاعده ۶ در CR-01).

| §۳۱ | مثال‌های ۲، ۴ و ۵: پیش‌نویس ERPNext جای خود را به Draft در Karyar با پیش‌نمایش، و Promote پس از تأیید می‌دهد |
| §۳۲ | ثبت سه پاسخ بالا به‌عنوان تصمیم تأییدشده |
| §۳۳ | تعارض شماره ۲ («بدون داده موازی») با وضعیت «حل‌شده» |

## نکته فنی برای فاز اول (spike)

- **محدودیت:** در ERPNext نسخه ۱۶، تابع عمومی `show_accounting_ledger_preview` به نام یک سند **ذخیره‌شده** نیاز دارد.
- **راه اصلی:** برای پیش‌نمایش بدون ذخیره، از تابع داخلی `get_accounting_ledger_preview(doc, filters)` روی سندِ در حافظه استفاده می‌شود (هر دو تابع در `erpnext/controllers/stock_controller.py` هستند).
- **راه جایگزین، در صورت بروز مشکل:** درج داخل یک savepoint تراکنش، محاسبه، و سپس rollback، که تضمین می‌کند چیزی ذخیره نمی‌شود.
- **کار لازم:** این مورد در فاز ۱ با یک آزمایش فنی کوتاه برای Sales Invoice و Journal Entry تأیید می‌شود.

# CR-03 — Human Task به‌عنوان محیط تعاملی انسان و ایجنت

## تصمیم

دخالت انسان (HITL) در Karyar فقط «تأیید یا رد» نیست. **Human Task یک محیط تعاملی بین انسان و ایجنت است.** انسان در محدوده‌ای که Workflow اجازه داده، این کارها را می‌تواند انجام دهد:

- مشاهده اطلاعات
- پرسیدن سؤال و خواستن توضیح
- افزودن، ویرایش یا حذف اطلاعات
- خواستن اطلاعات بیشتر از مشتری از طریق ایجنت
- تأیید، رد یا برگرداندن برای اصلاح
- توقف موقت (Pause) یا لغو (Cancel) پرونده
- تغییر مسیر بعدی، اگر Workflow اجازه داده باشد

قواعد بنیادی:

- **همه تعاملات، تغییرات و تصمیم‌ها ممیزی می‌شوند**، همراه با نسخه داده قبل و بعد از هر تغییر.
- **ایجنت فقط پیشنهاددهنده است.** نمی‌تواند به‌جای انسان تصمیم نهایی ثبت کند.
- **هویت و اختیار تصمیم فقط از کاربر احرازشده و مسئولِ همان Human Task می‌آید.** متن پیام‌ها و دستورهای مشتری هیچ اختیاری ایجاد نمی‌کنند.
- **HITL همچنان مبتنی بر Workflow و قابل پیکربندی است.** هر Workflow مشخص می‌کند Human Task کجا ساخته شود، مسئولش کیست، چه داده‌ای قابل مشاهده یا ویرایش است و چه سطح تأییدی لازم است.

## اقدام‌ها و قواعد هرکدام

| اقدام | چه کسی ثبت می‌کند | اثر | ممیزی |
|---|---|---|---|
| مشاهده | مسئول Task | فقط فیلدهای «قابل مشاهده» نمایش داده می‌شوند و بقیه پوشانده می‌شوند | ثبت دسترسی |
| سؤال و توضیح | مسئول، ایجنت پاسخ می‌دهد | ایجنت فقط با ابزارهای **خواندنی** و در محدوده **مشترکِ** مجوز گام و مجوز همین کاربر پاسخ می‌دهد (اجرا از طرف همین کاربر) | پیام‌ها و فراخوانی ابزارها |
| افزودن، ویرایش یا حذف | دستور از مسئول، اجرا با ایجنت یا مستقیم در فرم | فقط روی فیلدهای «قابل ویرایش». اعتبارسنجی با Schema. **یک نسخه جدید Draft** ساخته می‌شود | قبل و بعد هر فیلد، hash قبل و بعد، دستوردهنده، اجراکننده، پیام مرجع |
| درخواست اطلاعات از مشتری | مسئول | ایجنت پرسش را در گفت‌وگوی مشتری می‌فرستد و Task به وضعیت `waiting_customer` می‌رود. پاسخ مشتری یک نسخه جدید Draft می‌سازد که به نام **مشتری** ثبت می‌شود. Task دوباره باز می‌شود و تغییرات برجسته نمایش داده می‌شود | پرسش، پاسخ و نسخه جدید |
| تأیید | **فقط مسئول احرازشده** | تأیید به `payload_hash` آخرین نسخه Draft و hash پیش‌نمایش (CR-02) گره می‌خورد، با سطح `none`، `confirm` یا `strong` | متن خام، intent تفسیرشده، hash و شاهد تأیید (مثلاً OTP) |
| رد | فقط مسئول | پایان مسیر طبق Workflow. دلیل رد الزامی است | تصمیم و دلیل |
| برگرداندن برای اصلاح | فقط مسئول | در رویداد، نوع تصمیم `returned` همراه با دلیل و هدف (پیش‌فرض: ایجنت قبلی) ارسال می‌شود. n8n پرونده را به گام اصلاح برمی‌گرداند و بعد از اصلاح، Human Task جدیدی ساخته می‌شود | تصمیم و دلیل |
| توقف موقت و ادامه | فقط مسئول (یا نقش مدیر طبق Policy) | `Karyar Case.status = paused`. رویداد `case.paused` منتشر می‌شود. ادامه با `case.resumed` | تصمیم و دلیل |
| لغو پرونده | فقط مسئول (یا نقش مدیر)، با سطح پیش‌فرض `confirm` | `Karyar Case.status = cancelled` (پایانی). رویداد `case.cancelled` منتشر می‌شود. Draft طبق سیاست نگهداری مدیریت می‌شود | تصمیم و دلیل |
| تغییر مسیر | فقط مسئول، **فقط بین مسیرهای مجاز تعریف‌شده** | در رویداد، `route` منتقل می‌شود. Karyar عضویت `route` در `allowed_routes` را بررسی می‌کند | مسیر انتخاب‌شده و دلیل |

**تفاوت «اصلاح داخل Task» و «برگرداندن»:** اصلاح‌های کوچک داخل همان Task و بدون حرکت پرونده انجام می‌شوند. «برگرداندن» یک تصمیم در سطح Workflow است و پرونده را جابه‌جا می‌کند.

## ایجنت فقط پیشنهاددهنده است

- ابزارهای تصمیم‌گیری (`approve`، `reject`، `return`، `pause`، `cancel`، `change_route`) در اختیار ایجنت **نیستند**. ایجنت فقط `task.propose_decision` را دارد.
- تصمیم وقتی ثبت می‌شود که سیستم:
  1. احراز کند فرستنده، مسئولِ همین Task است. هویت از session کاربر می‌آید، نه از متن پیام.
  2. طبق سطح تأیید، خلاصه نهایی را نمایش دهد و تأیید صریح بگیرد.
- **ویرایش‌هایی که ایجنت انجام می‌دهد** به‌صورت «دستور از انسان، اجرا با ایجنت» ثبت می‌شوند. تفاوت قبل و بعد بلافاصله به انسان نشان داده می‌شود. اگر ایجنت دستوری را اشتباه فهمیده باشد، هنگام تأیید نهایی دیده می‌شود، چون خلاصه کامل و hash نمایش داده می‌شوند.
- **پیام‌های مشتری فقط داده‌اند.** هر تغییری که از سمت مشتری بعد از بازبینی انسان بیاید، Task را با برچسب «تغییرکرده پس از بازبینی» علامت می‌زند. تأییدهای قبلی تا بازبینی مجدد نامعتبر می‌شوند.

## پیکربندی برای هر Workflow

یک DocType کوچک به نام **`Human Task Template`** در Karyar تعریف می‌شود. n8n فقط با نام به آن ارجاع می‌دهد: `human_tasks.create(template, case_id, …)`.

| تنظیم | توضیح |
|---|---|
| `assignee_rule` | کاربر مشخص، Frappe Role یا نقش کاری. در صف نقش، Task توسط یک نفر «برداشته» می‌شود (claim) و برای دیگران قفل می‌شود |
| `visible_fields` / `masked_fields` | چه داده‌ای دیده شود |
| `editable_fields` | چه داده‌ای قابل افزودن، ویرایش یا حذف باشد |
| `required_fields` | پیش‌شرط امکان تأیید |
| `allowed_actions` | زیرمجموعه‌ای از اقدام‌های جدول بالا |
| `allowed_routes` | مسیرهای مجاز برای «تغییر مسیر» (مثلاً `doctor_review`، `skip_to_sales`) |
| `confirmation_level` | `none`، `confirm` یا `strong` برای تأیید. برای لغو، پیش‌فرض `confirm` است |
| `re_review_on_change` | بعد از تغییر مشتری یا ایجنت، آیا بازبینی مجدد لازم است |
| `can_ask_customer` | آیا انسان می‌تواند از مشتری اطلاعات بخواهد |

**چرا تنظیمات در Karyar است، نه در n8n؟** محدوده دید و ویرایش و سطح تأیید، **قاعده امنیتی** هستند و باید در Karyar اجرا شوند. n8n هنگام ساخت Task فقط می‌تواند این تنظیمات را **محدودتر** کند، **هرگز گسترده‌تر**. کف ایمنی تأیید در CR-02 هم مستقل از این تنظیمات برقرار است.

## نسخه‌داری داده و ممیزی

- **هر تغییر در Draft یک نسخه جدید می‌سازد.** هر نسخه این‌ها را ثبت می‌کند:
  - شماره نسخه
  - تفاوت در سطح فیلد (مقدار قبل و بعد)
  - hash قبل و بعد
  - منبع تغییر (`human`، `agent_on_behalf_of_human`، `customer` یا `system`)
  - کاربر
  - پیام مرجع
  - زمان
- این نسخه‌ها در همان **`Audit Log` فقط‌افزودنی** با نوع `draft.revised` ثبت می‌شوند. DocType جدیدی لازم نیست.
- **انواع رویداد ممیزی** در Human Task:
  - `task.created`، `task.claimed`، `task.viewed`، `task.message`، `task.tool_call`
  - `draft.revised`
  - `task.customer_info_requested` و `task.customer_info_received`
  - `task.decision_proposed` (توسط ایجنت)
  - `task.decided` (approve، reject، return، route)
  - `case.paused`، `case.resumed`، `case.cancelled`
  - `security.unauthorized_decision_attempt`

## هماهنگی با n8n (CR-01)

- **رویداد تصمیم:** رویداد `human_task.decided` شامل `decision` (approved، rejected، returned)، `route` و `reason` است. n8n روی همین فیلدها مسیر را انتخاب می‌کند (Switch). این یعنی تصمیم انسان، نه منطق داخل n8n.
- **اجرای Pause و Cancel در Karyar:** برای پرونده‌ای با وضعیت `paused` یا `cancelled`، API کاریار همه اقدام‌های کسب‌وکاری و Promote را **رد می‌کند**. حتی اگر یک Workflow در n8n به اجرا ادامه دهد، اثری در ERPNext ندارد. ادامه کار با رویداد `case.resumed` و از مرحله ثبت‌شده در Case انجام می‌شود.
- **«درخواست اطلاعات از مشتری»** داخل Karyar انجام می‌شود و به n8n نیازی ندارد. این قابلیت به CR-01 قاعده ۸ (گفت‌وگوی زنده در Karyar) وابسته است.

## رابط کاربری (Workspace)

صفحه Task دو بخش دارد:

1. **داده ساخت‌یافته:** فیلدها، تغییرات برجسته‌شده بین نسخه‌ها، و پیش‌نمایش ERPNext.
2. **گفت‌وگو با ایجنت.**

دکمه‌ها (تأیید، رد، برگرداندن، توقف، لغو، مسیرها) فقط میانبرهای اختیاری همان اقدام‌ها هستند. در فاز ۱، کارکنان فقط از طریق Workspace کار می‌کنند. انجام Human Task از پیام‌رسان (بله یا تلگرام) برای کارکنان به آینده موکول می‌شود. تأیید `strong` در هر حالت به session احرازشده Workspace نیاز دارد.

## دامنه فاز ۱

| در فاز ۱ | موکول‌شده |
|---|---|
| همه اقدام‌های جدول بالا با **یک مسئول** (کاربر یا صف نقش با claim) | تأیید چندنفره (M از N، ترتیبی یا موازی) |
| `Human Task Template`، نسخه‌داری Draft و ممیزی کامل | انجام Task از پیام‌رسان برای کارکنان |
| Workspace دوبخشی | مهلت و escalation خودکار (فعلاً یادآوری با Cron در n8n) |

## اصلاحات برنامه‌ریزی‌شده در سند اصلی

| بخش | تغییر |
|---|---|

| §۳۴ | گنجاندن دامنه فاز ۱ بالا در نقشه راه |

## موارد منتظر تأیید در CR-03

1. **تنظیمات Human Task در Karyar باشد** (`Human Task Template`) و n8n فقط بتواند آن را محدودتر کند، نه گسترده‌تر.
2. **لغو پرونده، اسنادی را که قبلاً در ERPNext ثبت شده‌اند خودکار لغو نمی‌کند.** لغو یا اصلاح سند ERPNext یک اقدام جدا و صریح است که سیاست تأیید (CR-02) بر آن اعمال می‌شود.
3. **«درخواست اطلاعات از مشتری»** به CR-01 قاعده ۸ (گفت‌وگوی زنده در Karyar) وابسته است. با تأیید CR-03، پیشنهاد می‌شود قاعده ۸ هم تأییدشده تلقی شود.

# CR-04 — بازطراحی HITL: Workspace مشترک انسان و ایجنت

## خلاصه تصمیم کاربر

1. **Human Task یک Workspace مشترک است.** پنل کاری و گفت‌وگو کنار هم هستند، ولی **تعامل اصلی گفت‌وگو است**، نه پر کردن فرم.
2. **اختیار انسان** همیشه از ترکیب Identity، Role، Responsibility و Permission در همان پروژه می‌آید.
3. **دامنه کارهای انسان:**
   - مشاهده اطلاعات
   - پرسیدن وضعیت و تاریخچه، و درخواست توضیح
   - افزودن، ویرایش و حذف اطلاعات، و اصلاح اطلاعات مشتری
   - درخواست جمع‌آوری اطلاعات جدید از مشتری
   - رد، برگرداندن به مرحله قبل، فرستادن به مرحله بعد، و واگذاری به فرد دیگر
   - Pause و ادامه
   - تغییر مسیر مجاز، و سایر اقدام‌های عملیاتی
4. **هر تغییری که انسان از طریق گفت‌وگو درخواست کند، پیش از ثبت باید توسط خود او تأیید شود.** ایجنت تغییر پیشنهادی را واضح نشان می‌دهد و فقط بعد از تأیید صریح انسان آن را ثبت می‌کند.
5. **«تصمیم شخصی ایجنت» وجود ندارد.** فقط تصمیم انسانی وجود دارد که با Identity و Permission همان انسان ثبت می‌شود.
6. **ممیزی کامل** شامل: درخواست انسان، برداشت ایجنت، تغییر پیشنهادی، تأیید، مقدار قبل و بعد، زمان، کاربر، Task، Workflow و نسخه داده. انسان باید بتواند از ایجنت درباره وضعیت، آخرین گفت‌وگو، آخرین تغییر، «چه کسی چه کرد» و مرحله فعلی بپرسد.
7. **تأیید چندنفره و قابل‌پیکربندی:** تأیید تک‌نفره، چندنفره، M از N، ترتیبی و موازی. تا شرط تأیید کامل نشده، ثبت نهایی انجام نمی‌شود.
8. **واگذاری کار بین ایجنت‌ها (Agent-to-Agent Delegation)** بر اساس مسئولیت، Policy و Workflow، نه اجرای آزاد. مثال: ایجنت مدیریت تکمیل اطلاعات مشتری را به Ava می‌سپارد.
9. **شناسه‌های کانال مشتری** (Instagram، Telegram، WhatsApp، تلفن، پیامک و…) به‌صورت ساخت‌یافته در CRM/ERP نگهداری شوند.
10. **واگذاری به Integration:** مثلاً «پیام تبلیغاتی به خریداران ماه گذشته». ایجنت مخاطبان را پیدا می‌کند، متن را آماده می‌کند، تأیید می‌گیرد و ارسال را به Integration پیامک واگذار می‌کند. همین الگو برای کانال‌های دیگر هم قابل استفاده است.
11. **وضعیت پیش‌ثبت (Pre-Registration/Draft)** هم در Karyar و هم در ERPNext قابل مشاهده و پیگیری باشد.

## تناقض‌ها با تصمیم‌های قبلی (صریح)

### T1 — پیش‌ثبت در ERPNext در برابر «Draft فقط در Karyar» (CR-02)

CR-02 می‌گوید: Draft اسناد مالی و پیچیده **فقط** در Karyar باشد، از ERPNext فقط پیش‌نمایش بدون ذخیره گرفته شود، و سند بعد از تأیید ساخته و ثبت شود. CR-04 می‌گوید: وضعیت پیش‌ثبت در ERPNext هم **قابل مشاهده و پیگیری** باشد.

**نکته کلیدی که تناقض را کوچک‌تر می‌کند:** Karyar و ERPNext **دو سیستم جدا نیستند.** هر دو اپ روی **یک Site و یک پایگاه داده Frappe** اجرا می‌شوند. پس `Karyar Case` همین حالا هم یک DocType در همان Desk است. می‌تواند در صفحه Customer یا Lead در بخش Connections نمایش داده شود و گزارش و فیلتر داشته باشد. «جدا شدن وضعیت بین دو سیستم» در این معماری به‌خودی‌خود رخ نمی‌دهد.

**تناقض واقعی فقط این است:** آیا قبل از تأیید، **سند کسب‌وکاری ERPNext** (مثلاً Sales Order یا Journal Entry با `docstatus=0`) ساخته شود یا نه؟

**گزینه‌ها (تصمیم با کاربر است؛ D1):**

| گزینه | شرح | مزایا | معایب |
|---|---|---|---|
| **A. فقط Karyar، با دیده‌شدن در ERPNext** | Draft فقط در `Karyar Case` می‌ماند. Case به اسناد ERPNext مرتبط (Customer، Lead، Item) لینک می‌شود و در Connections و یک نشانگر «پیش‌ثبت در جریان» دیده می‌شود. هیچ سند کسب‌وکاری قبل از تأیید ساخته نمی‌شود | سازگار کامل با CR-02؛ یک منبع ویرایش؛ بدون شلوغی و مصرف شماره‌گذاری | سند پیش‌ثبت در فهرست‌های بومی ERPNext (مثلاً فهرست Sales Order) دیده نمی‌شود |
| **B. پیش‌نویس بومی ERPNext** | از ابتدا سند ERPNext با `docstatus=0` ساخته و همان ویرایش می‌شود | دیده‌شدن کاملاً بومی؛ محاسبات ERPNext بدون نیاز به پیش‌نمایش | **دو محل ویرایش** (Desk و Karyar)، که تأیید هر تغییر، hash و ممیزی را دور می‌زند؛ مصرف شماره‌گذاری؛ برای Lead و Customer که حالت پیش‌نویس ندارند **ممکن نیست** (ساختن آن‌ها یعنی ثبت نهایی)؛ تناقض کامل با CR-02 |
| **C. ترکیبی (پیشنهاد)** | (۱) **منبع حقیقتِ پیش‌ثبت همیشه Draft در Karyar است.** (۲) گزینه A برای همه، به‌صورت پیش‌فرض. (۳) برای **اسناد ثبت‌شدنی** (Sales Order، Purchase Order، Invoice، Journal Entry و Payment Entry)، اگر Workflow بخواهد (`mirror_to_erp_draft`)، Karyar یک **پیش‌نویس آینه‌ای قفل‌شده** با `docstatus=0` در ERPNext می‌سازد که فیلد `karyar_case` و `karyar_locked=1` دارد. ویرایش آن در Desk با hookهای `validate` و `has_permission` **ممنوع** است. هر تغییرِ تأییدشده در Karyar، آینه را به‌روز می‌کند و در Promote همان سند Submit می‌شود. (۴) اطلاعات پایه (Lead، Customer، Contact) هرگز قبل از تأیید ساخته نمی‌شوند، جز گزینه «Lead ناقص» در CR-02 | دیده‌شدن بومی برای جایی که لازم است؛ همچنان یک محل ویرایش؛ سازگار با تأیید هر تغییر و hash | پیچیدگی متوسط (همگام‌سازی یک‌طرفه Karyar به ERPNext)؛ مصرف شماره‌گذاری در حالت آینه؛ CR-02 باید یک استثنای قابل‌پیکربندی بگیرد |

**نتیجه پیشنهادی (تأیید نشده):** گزینه C، با پیش‌فرض «A» و آینه فقط به‌انتخاب هر Workflow. در این حالت CR-02 به این صورت اصلاح می‌شود: «Draft در Karyar منبع حقیقتِ پیش‌ثبت است. ERPNext قبل از تأیید یا هیچ سندی ندارد، یا فقط آینه‌ای قفل‌شده و فقط‌خواندنی دارد.»

**داده دقیق در هر سیستم (با فرض گزینه C):**

| موضوع | در Karyar | در ERPNext قبل از ثبت نهایی | در ERPNext بعد از ثبت نهایی |
|---|---|---|---|
| مشتری یا Lead جدید | Draft شامل فیلدها، شناسه‌های کانال، نسخه‌ها، تأییدها، گفت‌وگو | هیچ سندی. Case در Desk قابل مشاهده است (یا «Lead ناقص» اگر روشن باشد) | Lead یا Customer، Contact به‌همراه جدول کانال‌ها، و ارجاع در Case |
| اصلاح اطلاعات مشتری موجود | Change Proposal (فقط دلتا: قبل و بعد) | Contact یا Customer **بدون تغییر**. Case در Connections همان مشتری با برچسب «تغییر در انتظار» | Contact یا Customer به‌روز. ممیزی در Karyar و Version در Frappe |
| سفارش و پیش‌فاکتور | Draft، نسخه‌ها، پیش‌نمایش (hash)، تأییدها | **A:** هیچ سندی (Case قابل مشاهده). **C3:** سند آینه‌ای `docstatus=0` قفل‌شده | سند Submitشده. آینه همان سند می‌شود |
| اسناد مالی (Invoice، Payment Entry، Journal Entry) | همان | همان (پیش‌فرض A) | سند Submitشده و ثبت‌های دفتر کل |
| کمپین پیام انبوه | Case از نوع کمپین: معیار انتخاب، **فهرست ارجاع به Contactها** (نه کپی)، نسخه‌های متن، تأییدها، وضعیت ارسال هر گیرنده | (اختیاری) لینک به `Campaign` در ERPNext | خلاصه ارسال. (اختیاری) `Communication` برای هر گیرنده یا خلاصه روی Campaign |

### T2 — تأیید چندنفره در فاز ۱

CR-01 و CR-03 تأیید «M از N» را به آینده موکول کرده بودند. CR-04 آن را جزو معماری می‌خواهد.

**پیشنهاد:** با یک **مدل یکپارچه** همه حالت‌ها به یک ساختار تبدیل می‌شوند و پیاده‌سازی ارزان می‌شود (بخش «مدل تأیید» پایین). **پیشنهاد می‌شود از فاز ۱ پیاده شود.** فقط مهلت و escalation خودکار به آینده موکول می‌شود. (D3)

### T3 — واگذاری بین ایجنت‌ها در برابر «n8n موتور Workflow» (CR-01)

اگر هر واگذاری از n8n عبور کند، کار درون یک Task (مثلاً «Ava اطلاعات را از مشتری بگیرد») کند و شکننده می‌شود. اگر هیچ واگذاری از n8n عبور نکند، n8n از جریان کار بی‌خبر می‌ماند.

**پیشنهاد مرز (D4):**

- **واگذاری درون یک Task** (کمک به انجام همین مرحله) در **خود Karyar** اجرا می‌شود و یک `Agent Task` فرزند می‌سازد. نتیجه به همان Human Task برمی‌گردد.
- **حرکت پرونده بین مراحل فرایند** همچنان با n8n است.
- **واگذاری به Integration** (ارسال پیامک، WhatsApp و…) با **n8n اجرا می‌شود**، ولی آغاز، مجوز و ثبت آن در Karyar است.
- برای این کار یک **فهرست حداقلی از Integration Targetها** لازم است: نام، آدرس Workflow در n8n، Schema ورودی، توانمندی لازم و سیاست تأیید. این نسخه **بسیار کوچک‌شده‌ای از CR-01a** است که در عمل لازم می‌شود. (D5)

## مدل اختیار انسان

**اختیار مؤثر = Identity × Frappe Roles/Permissions × Responsibility × Template × Approval Policy**

| لایه | تعیین می‌کند | محل |
|---|---|---|
| Identity | چه کسی است. Session احرازشده (و 2FA برای سطح `strong`) | Frappe User |
| Frappe Roles و User Permission | به **چه داده‌ای** دسترسی دارد (سند، رکورد، فیلد، شعبه یا واحد) | Frappe |
| **Responsibility (برای انسان)** | چه **نقش کاری** در فرایندها دارد. مثلاً «بازبین پذیرش» یا «تأییدکننده مالی» | `Role Assignment` در هر Tenant (همان مفهوم ایجنت‌ها، §۵.۱) |
| Human Task Template | در **این مرحله** چه اقدام‌هایی مجاز است | Karyar |
| Approval Policy | آیا **واجد شرایط تأیید** این عملیات است | Karyar |

- **«پروژه»** فعلاً برابر با Tenant (Site) تفسیر می‌شود. محدوده‌های داخلی مثل شعبه یا واحد با User Permission اعمال می‌شوند. (D7)
- **درخواست خارج از اختیار:** ایجنت صریحاً می‌گوید خارج از حوزه اختیار کاربر است و بر اساس جدول Responsibilityها پیشنهاد می‌دهد چه کسی صلاحیت دارد. اگر Template اجازه دهد، پیشنهاد واگذاری به همان فرد را هم می‌دهد. رویداد `security.out_of_scope_request` ثبت می‌شود.

## الگوی «پیشنهاد تغییر» (Change Proposal) — تأیید هر تغییر

<pre class="ltr">
Human: "Change the customer's mobile to 0935…"
 → Agent interprets → ChangeProposal{target, field, before, after, interpretation, scope_check}
 → Agent shows: "Mobile: 0912… → 0935… — confirm?"
 → Human (authenticated assignee) confirms explicitly ("yes" in session, or button)
 → apply: Draft target → new revision | finalized ERPNext record → update via business action (+ Approval Policy floor)
 → Audit: request(raw) · interpretation · proposal(before/after) · confirmation(who/when/how) · result · versions
</pre>

- **همه تغییرهایی که از گفت‌وگو می‌آیند** (افزودن، ویرایش، حذف) از این مسیر می‌گذرند. تغییر مستقیم در پنل فرم هم یک تأیید صریح است: کلیک «ذخیره» پس از نمایش تفاوت. (D8)
- **چند تغییر** را می‌توان در یک Proposal دسته‌بندی کرد تا یک‌جا تأیید شوند.
- **تفکیک دو مفهوم:**
  - **تأیید تغییر (Change Confirmation):** درخواست‌کننده تأیید می‌کند که ایجنت درست فهمیده است.
  - **تأیید مجوز (Approval):** فرد یا افراد واجد شرایط، طبق Approval Policy اجازه ثبت نهایی می‌دهند.
  
  یک نفر ممکن است هر دو کار را انجام دهد، ولی دو رکورد جداگانه ثبت می‌شود.
- **تغییر روی داده نهایی ERPNext** (مثلاً شماره مشتری موجود) یک «به‌روزرسانی داده نهایی» است و کف ایمنی تأیید (CR-02) برای آن هم اعمال می‌شود.
- **این بند جایگزین بند «ویرایش‌هایی که ایجنت انجام می‌دهد» در CR-03 است.**

## «تصمیم شخصی ایجنت» وجود ندارد

- **ایجنت این کارها را انجام می‌دهد:** فهمیدن، پیشنهاد دادن، اجرای تغییرِ تأییدشده، هماهنگی، و واگذاری در محدوده Policy.
- **ایجنت این کارها را انجام نمی‌دهد:** تأیید تغییر، تأیید مجوز، انتخاب مسیر، رد، لغو یا Pause.
- **اجرای خودکار بدون حضور انسان** (مثل مثال ۵ سند: ثبت خودکار سفارش مشتری معتبر) **تصمیم ایجنت نیست.** این یک **تصمیم انسانیِ از پیش گرفته‌شده** است که در Workflow یا Policy کدگذاری شده است. ممیزی هر اجرای خودکار شامل **نسخه Policy و کاربری که آن را تعریف یا فعال کرده** است. به این ترتیب هر اقدام نهایی به یک تصمیم انسانی قابل ردیابی وصل است: یا تأیید لحظه‌ای، یا Policy مصوب. (D2)

## مدل تأیید چندنفره (یکپارچه)

<pre class="ltr">
Approval Policy (per action type / workflow, versioned)
  stages: [                                   # ordered → Sequential
    { eligible: users | roles | responsibilities | expression,
      required: M,                            # 1 = Single, M<N = M-of-N, M=N = all (Parallel)
      exclude_requester: true }               # no self-approval
  ]
  invalidate_on_change: all | later_stages    # any change after an approval resets approvals
  reject_rule: any_reject_rejects | count_based
  confirmation_level: none | confirm | strong
</pre>

| ساختار | بیان در مدل |
|---|---|
| Single Approval | یک مرحله با `required=1` |
| Multi Approval / Parallel | یک مرحله با N واجد شرایط و `required=N`؛ همه همزمان |
| M-of-N | یک مرحله با `required=M` |
| Sequential | چند مرحله پشت سر هم |
| ترکیبی | مثلاً مرحله ۱: یکی از سرپرست‌ها؛ مرحله ۲: ۲ از ۳ مدیر |

- **DocType جدید `Approval Request`:** مراحل، تأییدهای جمع‌شده، hash تأییدشده و وضعیت را نگه می‌دارد. هر تأییدکننده یک Human Task از نوع `approval` در Workspace خودش دارد که به این Request لینک شده است.
- **کف ایمنی در CR-02** در زمان Promote بررسی می‌کند که `Approval Request` با **همان hash** کامل شده باشد. تا کامل نشدن، «فرستادن به مرحله بعد» و Promote **مسدود** است.
- **فاز ۱:** کل مدل. **آینده:** مهلت، escalation و جایگزین (delegate approver).

## واگذاری بین ایجنت‌ها (Agent-to-Agent Delegation)

- **`Delegation Policy`** (جدول در `Karyar Settings`) مشخص می‌کند:
  - کدام Responsibility می‌تواند به کدام Responsibility یا Integration Target کار بسپارد
  - با کدام توانمندی‌ها
  - آیا تأیید انسانی لازم است
  - سقف دامنه کار (مثلاً فقط مخاطبانِ همین پرونده)
  - محدودیت تعداد
- **DocType جدید `Agent Task`:**
  - والد (Case یا Human Task)
  - درخواست‌دهنده: ایجنت، **از طرف کدام انسان**، و بر اساس کدام Policy
  - مقصد (Responsibility یا ایجنت، یا Integration Target)
  - دستور کار ساخت‌یافته و ورودی‌ها (ارجاع، نه کپی)
  - وضعیت: `queued`، `running`، `waiting_customer`، `completed`، `failed` یا `cancelled`
  - نتیجه ساخت‌یافته، و زنجیره واگذاری
- **جلوگیری از افزایش اختیار (Confused Deputy):** اختیار کار واگذارشده برابر است با **اشتراکِ** اختیار انسانِ آغازگر، توانمندی ایجنت واگذارکننده، توانمندی ایجنت مقصد و Delegation Policy. هیچ زنجیره واگذاری نمی‌تواند به اختیاری بیش از انسان آغازگر برسد.
- **محدودیت عمق** (پیش‌فرض ۲) و **جلوگیری از چرخه.** همه حلقه‌های زنجیره در ممیزی ثبت می‌شوند.
- **بازگشت نتیجه:** رویداد `agent.task.completed` منتشر می‌شود. نتیجه در گفت‌وگوی Human Task نمایش داده می‌شود. اگر نتیجه داده را تغییر دهد، به‌صورت **Change Proposal** به انسان ارائه می‌شود.
- **مثال:** مدیر از ایجنت مدیریت می‌خواهد اطلاعات ناقص مشتری را کامل کند.
  1. Policy واگذاری از «مدیریت» به «پذیرش مشتری» را مجاز می‌داند.
  2. یک `Agent Task` برای Ava ساخته می‌شود.
  3. Ava از روی شناسه‌های کانال مشتری که در ERPNext ثبت است، با مشتری تماس می‌گیرد.
  4. پاسخ مشتری به‌عنوان نسخه جدید Draft و با منبع «مشتری» ثبت می‌شود.
  5. نتیجه به Workspace مدیر برمی‌گردد.

## واگذاری به Integration و مثال کمپین پیام

1. **مدیر در Workspace:** «به همه مشتریانی که در یک ماه گذشته خرید داشته‌اند پیام تبلیغاتی بفرست.»
2. **ایجنت مدیریت مخاطبان را پیدا می‌کند**، با گزارش کنترل‌شده Karyar (`customers_with_purchases(period)`) و در محدوده مجوز مدیر. خروجی: تعداد، نمونه، و **فیلتر رضایت دریافت پیام** (opt-in/opt-out) برای هر کانال.
3. **متن پیام** پیشنهاد می‌شود. هر اصلاح متن با Change Proposal تأیید می‌شود.
4. **Approval Policy عملیات `marketing.bulk_send`** اعمال می‌شود (مثلاً مدیر به‌علاوه مسئول بازاریابی). تأیید به hash «فهرست گیرندگان + متن» گره می‌خورد.
5. **واگذاری** طبق Delegation Policy به Integration Target ‏`messaging.sms.bulk_send` انجام می‌شود. Karyar یک `Agent Task` می‌سازد و Workflow مربوط در n8n را فراخوانی می‌کند. n8n:
   - به‌صورت دسته‌ای ارسال می‌کند
   - محدودیت نرخ و فهرست انصراف را رعایت می‌کند
   - وضعیت هر گیرنده را با callback برمی‌گرداند
6. **گزارش نهایی** به مدیر داده می‌شود و همه مراحل ممیزی می‌شوند.

همین الگو برای WhatsApp، Telegram، Instagram و بله فقط با Integration Target دیگر کار می‌کند.

> ⚠️ **محدودیت‌های کانال (واقعیت، نه تصمیم):**
> - WhatsApp Business برای پیام آغازشده توسط کسب‌وکار، **قالب پیام تأییدشده و رضایت کاربر** لازم دارد.
> - Instagram معمولاً فقط در **پنجره زمانی پس از آخرین پیام کاربر** اجازه پاسخ می‌دهد.
> - ربات Telegram یا بله فقط به کاربری پیام می‌دهد که **قبلاً ربات را آغاز کرده** است.
> - پیامک تبلیغاتی در ایران **قواعد خطوط تبلیغاتی و انصراف** دارد.
>
> پس Integration Target هر کانال باید محدودیت‌های خودش را اعلام کند و ایجنت باید از روی داده رضایت و کانال، مخاطبانِ **قابل‌ارسال** را جدا کند. API رسمی Meta برای کسب‌وکار ایرانی همچنان ریسک باز است (§۲۸ سند).

## شناسه‌های کانال مشتری در ERPNext

ERPNext نسخه ۱۶ در Contact فقط تلفن و ایمیل دارد (`phone_nos`، `email_ids`، `mobile_no`، `unsubscribed`). Lead فیلد `whatsapp_no` دارد. فیلدی برای Telegram، Instagram یا بله **وجود ندارد**.

**پیشنهاد:**

- یک **جدول فرزند سفارشی `Contact Channel`** روی Contact (به‌صورت fixture، بدون تغییر هسته) با فیلدهای:
  - `channel` (telegram، instagram، whatsapp، bale، sms، phone، email، web)
  - `identifier`
  - `display_handle`
  - `verified`
  - `consent_marketing`
  - `opted_out_at`
  - `last_inbound_at` (برای پنجره زمانی کانال‌ها)
  - `is_primary`
  - `source_case`
- Lead و Customer از طریق `links` در Contact به این جدول دسترسی دارند.
- **قبل از ثبت نهایی**، شناسه کانال در Draft و Conversation است. در Promote به `Contact Channel` منتقل می‌شود.
- **DocType ‏`Contact Identity` داخل Karyar حذف می‌شود.** ERPNext منبع حقیقت شناسه‌هاست. Karyar فقط برای مسیریابی پیام‌های ورودی یک کش جست‌وجو یا index دارد که از ERPNext ساخته می‌شود. (D6)

## Workspace مشترک انسان و ایجنت (UI)

- **بخش اصلی (گفت‌وگو):** دستور، پرسش وضعیت و تاریخچه، دریافت پیشنهاد تغییر و تأیید آن، و واگذاری.
- **پنل کناری:**
  - داده ساخت‌یافته و تفاوت نسخه‌ها
  - کارت‌های **Change Proposal در انتظار** (با دکمه تأیید)
  - **وضعیت Approval** (مراحل، چه کسی تأیید کرده، چه کسی مانده)
  - خط زمانی (Timeline)
  - **Agent Taskهای واگذارشده** و وضعیتشان
  - پیش‌نمایش ERPNext
- **ابزارهای پرسش وضعیت** (همه فقط‌خواندنی و فیلترشده با مجوز کاربر و پوشاندن فیلدها):
  - `case.status`
  - `case.timeline(filter)`، برای «چه کسی چه تغییری داد»
  - `task.history`
  - `draft.diff(rev_a, rev_b)`
  - `conversation.last_summary`
- **اقدام‌های حرکت‌دهنده:**
  - برگرداندن به مرحله قبل (`returned`)
  - فرستادن به مرحله بعد (`approved`/`forwarded`، فقط اگر Approval کامل باشد)
  - واگذاری به فرد دیگر (`reassign`، فقط به فرد دارای Responsibility واجد شرایط؛ داخلی و بدون n8n)
  - Pause و Resume
  - تغییر مسیر مجاز
  - Cancel
  
  همه با بررسی Permission و Template انجام می‌شوند. اقدام‌های سطح Workflow به‌صورت رویداد به n8n می‌روند.
