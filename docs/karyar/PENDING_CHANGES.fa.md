# CR-01 — Workflow در فاز اول با n8n

## تصمیم

در فاز اول، Workflow Engine اختصاصی در Karyar ساخته **نمی‌شود**. n8n خودمیزبان محل ساخت و اجرای Workflowها و Automationهاست.

- **Karyar:** ایجنت‌ها، منطق کسب‌وکار، ERPNext، داده، مجوز و APIها
- **n8n:** ترتیب گام‌ها، مسیریابی بین ایجنت‌ها، triggerها، اعلان‌ها و اتصال به سرویس‌های بیرونی

**اصل راهنما:** «n8n ترتیب کارها را تعیین می‌کند؛ Karyar تصمیم می‌گیرد و اجرا می‌کند.»

**دلیل:** تیم و زیرساخت ساخت موتور اختصاصی فعلاً وجود ندارد. n8n آشناست، خودمیزبان اجرا می‌شود و رسیدن به اولین مشتری را سریع‌تر می‌کند. اگر بعداً لازم شد، منطق به موتور داخلی منتقل می‌شود.

## محل ساخت و نگهداری Workflowها

- **ساخت و اجرا:** در n8n خودمیزبان، با دو نمونه جدا برای test و production.
- **نسخه‌داری:** export به JSON در `karyar-deploy/n8n/workflows/`. اعتبارنامه‌ها در git ذخیره نمی‌شوند.
- **مستندسازی:** کنار هر Workflow یک `README` با Trigger، گام‌ها و endpointهای Karyar که صدا زده می‌شوند. این فایل‌ها پایه انتقال آینده‌اند.
- **نام‌گذاری:** `KY | <process> | <segment>`

## قواعد سخت n8n

1. n8n **فقط** با Karyar API v1 کار می‌کند. نوشتن یا خواندن مستقیم از ERPNext (نود ERPNext یا `/api/resource`) و دسترسی به پایگاه داده ممنوع است.
2. **منطق کسب‌وکار در Code Node ممنوع است.** Code Node فقط برای نگاشت و قالب‌بندی داده است.
3. n8n روی **پرچم‌هایی که Karyar برمی‌گرداند** شرط می‌گذارد (مثلاً `requires_approval`). خودش محاسبه کسب‌وکاری انجام نمی‌دهد.
4. نودهای AI Agent در n8n به‌جای ایجنت‌های Karyar استفاده نمی‌شوند.
5. **Workflowها کوتاه و زنجیره‌ای‌اند.** Wait چندروزه برای انتظار انسان ممنوع است. وضعیت پرونده در `Karyar Case` نگه داشته می‌شود.
6. n8n **Draft و داده کسب‌وکاری نگه نمی‌دارد.** فقط `case_id` و حداقل فیلدهای لازم منتقل می‌شوند. ذخیره داده اجراهای موفقِ جریان‌های حساس خاموش است و داده‌های اجرا به‌صورت خودکار حذف می‌شوند (pruning).
7. **`case_id` و `correlation_id` در همه فراخوانی‌ها منتقل می‌شوند.** شناسه execution در n8n روی Case ثبت می‌شود.
8. گفت‌وگوی زنده ایجنت با مشتری در Channel Gateway داخل Karyar می‌ماند. فقط **نتیجه** گفت‌وگو به n8n می‌رود. ⏳ *منتظر تأیید نهایی*

## اتصال

| جهت | سازوکار |
|---|---|
| Karyar ← n8n | رویدادهای ERPNext از DocType ‏Webhook خود Frappe (شرط‌گذاری، HMAC و لاگ). رویدادهای Karyar مثل `intake.completed`، `human_task.decided` و `agent.task.completed` با یک تابع کوچک `emit_event()` که بعد از commit اجرا می‌شود |
| n8n ← Karyar | نود HTTP Request به Karyar API v1 با کلید API کاربر `n8n@karyar` (دسترسی حداقلی). زیرWorkflow مشترک «Call Karyar» برای احراز هویت و خطاها |
| n8n و ایجنت‌ها | `agents.run_task` ناهمگام است. پایان کار ایجنت با رویداد `agent.task.completed` به n8n اعلام می‌شود |
| n8n و انسان | n8n با `human_tasks.create` کار انسانی را می‌سازد و Workflow تمام می‌شود. تصمیم انسان با رویداد `human_task.decided` مرحله بعد را شروع می‌کند |

**پاسخ سؤال‌های قبلی:**
- اعلان‌ها (پیامک، ایمیل، پیام اطلاع‌رسانی) از n8n ارسال می‌شوند.
- اعتبارنامه سرویس‌های بیرونی در n8n نگه داشته می‌شود.

## پیاده‌سازی در فاز اول

- **Karyar:**
  - DocTypeها: `Karyar Agent`، `Conversation`، `Message`، `Karyar Case`، `Human Task`، `Audit Log`، `AI Usage Log`، `Karyar Settings`
  - اجرای ساده ایجنت، و یک wrapper برای مدل AI که مصرف را ثبت می‌کند
  - ۸ تا ۱۵ ابزار پایلوت
  - ۸ تا ۱۰ endpoint در API v1، همه با `idempotency_key`
  - تابع `emit_event()` و Webhookهای Frappe
  - چت مشتری و Workspace حداقلی
  - نرمال‌سازی و اعتبارسنج‌های فارسی
  - قانون semgrep
- **n8n:**
  - Docker با Postgres در شبکه خصوصی
  - pruning داده‌های اجرا
  - زیرWorkflow «Call Karyar» و Error Workflow
  - ۳ تا ۵ Workflow پایلوت
  - اسکریپت export به git

## موکول‌شده به آینده

- Workflow Engine داخلی
- Automation Gateway، Action Contract، Adapter و Integration Job
- Outbox و Event Bus اختصاصی
- تأیید موازی «M از N» و escalation پیشرفته
- سازنده گرافیکی
- چندمستأجری n8n (برای مشتری اول یک n8n کافی است)
- RPA، مودیان، MCP، حافظه بلندمدت، مدیریت کامل هزینه، LiteLLM و Control Plane

## ریسک‌های ثبت‌شده

- تست و بازبینی منطق ترتیبی در n8n سخت‌تر است.
- Webhook خود Frappe در صورت شکست، خودکار retry نمی‌کند. راه کاهش: لاگ خطا، به‌علاوه یک Workflow زمان‌بندی‌شده که «پرونده‌های بی‌حرکت» را از Karyar می‌پرسد.
- عیب‌یابی بین دو سیستم سخت‌تر است. راه کاهش: `correlation_id` در همه فراخوانی‌ها.
- مجوز Sustainable Use در n8n قبل از فروش تجاری باید بررسی شود.

## CR-01a — جایگزین‌شده

پیشنهاد قبلی شامل Automation Gateway، Action Contract، Executor Binding، Adapterها و `Integration Job` در فاز اول اجرا **نمی‌شود**. جای آن را قواعد ۱ تا ۸ بالا می‌گیرند. این پیشنهاد به‌عنوان مسیر احتمالی آینده در §۳۰ ثبت می‌شود.

# CR-02 — مرز داده Karyar و ERPNext

## تصمیم

| دسته | چه چیزی | کجا | عمر |
|---|---|---|---|
| **Karyar Draft** | اطلاعات ناقص، پیش‌نویس، تغییرات پیشنهادی، داده در حال تکمیل | `Karyar Case.draft_data` و payload در `Human Task` | تا ثبت نهایی (Promote) یا رها شدن |
| **Conversation Context** | پیام‌ها و خلاصه تعامل | `Conversation` و `Message`، و فیلد `summary` | طبق سیاست نگهداری |
| **داده نهایی کسب‌وکار** | Lead، مشتری، سفارش، سند حسابداری و… | **ERPNext (Source of Truth)** | دائمی |
| **سوابق فرایند** (کمکی) | مرحله پرونده، ارجاع به اسناد ERPNext، تصمیم‌ها، ممیزی، مصرف AI | Karyar | دائمی |

**چرخه عمر:** گفت‌وگو ← Draft در Karyar ← (تأیید مشتری؟) ← (تأیید انسانی؟) ← **Promote** ← ERPNext.

پس از Promote، Case فقط **ارجاع** و snapshot ممیزی را نگه می‌دارد. دو تأیید داخل پرانتز اختیاری‌اند و برای هر Workflow قابل تنظیم‌اند.

## پاسخ‌های تأییدشده

1. **Draft اسناد مالی و پیچیده در Karyar می‌ماند.**
   - برای محاسباتی که متعلق به ERPNext است (مالیات، جمع‌ها، ثبت‌های دفتر کل)، فقط **پیش‌نمایش بدون ذخیره** از ERPNext گرفته می‌شود.
   - بعد از تأیید، سند نهایی در ERPNext ساخته و ثبت (Submit) می‌شود.
   - محاسبات ERPNext در Karyar بازنویسی **نمی‌شوند**.
2. **Draftهای ناقص و رهاشده** با مدت نگهداری **قابل تنظیم برای هر Workflow** مدیریت می‌شوند.
   - ۳۰ روز فقط **مقدار پیش‌فرض** است، نه قانون ثابت.
   - امکان ثبت «Lead ناقص» برای هر Workflow قابل تنظیم است و **پیش‌فرض آن خاموش** است.
3. **کف ایمنی تأیید در Karyar وجود دارد.**
   - اگر عملیاتی طبق Policy نیاز به تأیید داشته باشد، Karyar ثبت نهایی در ERPNext را **بدون تأیید معتبر رد می‌کند**.
   - این قاعده حتی وقتی Workflow در n8n گام تأیید را جا انداخته باشد اعمال می‌شود.

## قواعد (متن نهایی برای سند)

1. **Draft فقط «دلتا» نگه می‌دارد.** برای موجودیت‌هایی که در ERPNext وجود دارند، فقط ارجاع به‌علاوه اطلاعات جدید یا تغییرکرده ذخیره می‌شود. تغییرات اطلاعات پایه در گام Promote روی ERPNext اعمال می‌شوند.
2. **Promote یک endpoint واحد در Karyar است** که n8n صدا می‌زند. این endpoint به ترتیب:
   1. کامل بودن داده را طبق Schema بررسی می‌کند.
   2. سیاست تأیید را بررسی می‌کند (قاعده ۳).
   3. با `idempotency_key` در ERPNext ثبت می‌کند.
   4. ارجاع (`doctype`/`name`) را روی Case ذخیره می‌کند.
   5. Draft را «منتقل‌شده» علامت می‌زند و قفل می‌کند.
3. **سیاست تأیید (کف ایمنی):**
   - یک جدول ساده در `Karyar Settings` با ستون‌های: نوع عملیات، نیاز به تأیید، نقش تأییدکننده، سطح تأیید (`none`، `confirm` یا `strong`).
   - Promote وقتی موفق می‌شود که برای عملیات‌های فهرست‌شده یک **Human Task تأییدشده** وجود داشته باشد که `payload_hash` آن **دقیقاً با Draft فعلی یکی باشد**. در غیر این صورت درخواست رد می‌شود و رویداد `security.approval_missing` ثبت می‌شود.
   - عملیاتی که در این جدول نیست، بدون تأیید مجاز است.
   - اینکه Workflow گام تأیید داشته باشد یا نه، همچنان در n8n تعیین می‌شود. این جدول فقط **کف** را تعیین می‌کند.
4. **پیش‌نمایش ERPNext بدون ذخیره:**
   - سند ERPNext در حافظه ساخته می‌شود و محاسبات خود ERPNext روی آن اجرا می‌شود (مثل `calculate_taxes_and_totals`، و برای اسناد حسابداری `get_accounting_ledger_preview`). سپس نتیجه بدون ذخیره برگردانده می‌شود.
   - این پیش‌نمایش به تأییدکننده نمایش داده می‌شود و **hash آن بخشی از آن چیزی است که تأیید می‌شود.**
   - در زمان Promote، اگر محاسبه مجدد نتیجه متفاوتی بدهد (مثلاً نرخ یا موجودی تغییر کرده باشد)، Promote متوقف می‌شود و تأیید دوباره لازم است.
5. **بعد از Promote، ایجنت داده اصلی را فقط از ERPNext می‌خواند.** context ایجنت شامل ارجاع‌ها و مرحله از Case، به‌علاوه داده تازه با ابزارها از ERPNext است. Draft قفل‌شده و snapshot در دسترس ابزارهای ایجنت **نیستند**.
6. **اصلاح بعد از ثبت نهایی فقط روی ERPNext** انجام می‌شود، از طریق اقدام کسب‌وکاری Karyar. در صورت لغو و اصلاح سند (Amend)، Case به سند جدید ارجاع می‌دهد.
7. **snapshot تأییدشده فقط برای ممیزی** نگه داشته می‌شود. فقط‌خواندنی است و داده شخصی آن بعد از دوره نگهداری قابل پاک‌سازی است.
8. **خلاصه مکالمه** قصد، ترجیحات، سؤال‌های باز، قول‌های داده‌شده و لحن را نگه می‌دارد. واقعیت‌های کسب‌وکاری در خلاصه با برچسب «طبق گفته مشتری در تاریخ X» ثبت می‌شوند و ایجنت برای واقعیت‌ها **همیشه** از ERPNext استفاده می‌کند.
9. **سابقه مکالمات قبلی:** هر Conversation به Contact/Lead/Customer در ERPNext متصل است. ایجنت خلاصه چند مکالمه آخر **همان مخاطب** را می‌بیند. DocType جدیدی لازم نیست.
10. **Draft رهاشده:**
    - بعد از مدت نگهداری Workflow (پیش‌فرض ۳۰ روز)، Case با وضعیت `abandoned` بسته و داده شخصی Draft پاک می‌شود.
    - اگر گزینه «ثبت Lead ناقص» برای آن Workflow روشن باشد، **قبل از** پاک‌سازی، یک Lead با وضعیت «ناقص» در ERPNext ساخته می‌شود.
    - کف ایمنی تأیید برای این Lead هم اعمال می‌شود، اگر در Policy تعریف شده باشد.
11. **n8n هیچ‌وقت Draft نگه نمی‌دارد** (همان قاعده ۶ در CR-01).

- **راه اصلی:** برای پیش‌نمایش بدون ذخیره، از تابع داخلی `get_accounting_ledger_preview(doc, filters)` روی سندِ در حافظه استفاده می‌شود (هر دو تابع در `erpnext/controllers/stock_controller.py` هستند).
- **راه جایگزین، در صورت بروز مشکل:** درج داخل یک savepoint تراکنش، محاسبه، و سپس rollback، که تضمین می‌کند چیزی ذخیره نمی‌شود.
- **کار لازم:** این مورد در فاز ۱ با یک آزمایش فنی کوتاه برای Sales Invoice و Journal Entry تأیید می‌شود.

# CR-03 — Human Task به‌عنوان محیط تعاملی انسان و ایجنت

## تصمیم

دخالت انسان (HITL) در Karyar فقط «تأیید یا رد» نیست. **Human Task یک محیط تعاملی بین انسان و ایجنت است.** انسان در محدوده‌ای که Workflow اجازه داده، این کارها را می‌تواند انجام دهد:

- مشاهده اطلاعات
- پرسیدن سؤال و خواستن توضیح
- افزودن، ویرایش یا حذف اطلاعات
- خواستن اطلاعات بیشتر از مشتری از طریق ایجنت
- تأیید، رد یا برگرداندن برای اصلاح
- توقف موقت (Pause) یا لغو (Cancel) پرونده
- تغییر مسیر بعدی، اگر Workflow اجازه داده باشد

قواعد بنیادی:

- **همه تعاملات، تغییرات و تصمیم‌ها ممیزی می‌شوند**، همراه با نسخه داده قبل و بعد از هر تغییر.
- **ایجنت فقط پیشنهاددهنده است.** نمی‌تواند به‌جای انسان تصمیم نهایی ثبت کند.
- **هویت و اختیار تصمیم فقط از کاربر احرازشده و مسئولِ همان Human Task می‌آید.** متن پیام‌ها و دستورهای مشتری هیچ اختیاری ایجاد نمی‌کنند.
- **HITL همچنان مبتنی بر Workflow و قابل پیکربندی است.** هر Workflow مشخص می‌کند Human Task کجا ساخته شود، مسئولش کیست، چه داده‌ای قابل مشاهده یا ویرایش است و چه سطح تأییدی لازم است.

## اقدام‌ها و قواعد هرکدام

| اقدام | چه کسی ثبت می‌کند | اثر | ممیزی |
|---|---|---|---|
| مشاهده | مسئول Task | فقط فیلدهای «قابل مشاهده» نمایش داده می‌شوند و بقیه پوشانده می‌شوند | ثبت دسترسی |
| سؤال و توضیح | مسئول، ایجنت پاسخ می‌دهد | ایجنت فقط با ابزارهای **خواندنی** و در محدوده **مشترکِ** مجوز گام و مجوز همین کاربر پاسخ می‌دهد (اجرا از طرف همین کاربر) | پیام‌ها و فراخوانی ابزارها |
| افزودن، ویرایش یا حذف | دستور از مسئول، اجرا با ایجنت یا مستقیم در فرم | فقط روی فیلدهای «قابل ویرایش». اعتبارسنجی با Schema. **یک نسخه جدید Draft** ساخته می‌شود | قبل و بعد هر فیلد، hash قبل و بعد، دستوردهنده، اجراکننده، پیام مرجع |
| درخواست اطلاعات از مشتری | مسئول | ایجنت پرسش را در گفت‌وگوی مشتری می‌فرستد و Task به وضعیت `waiting_customer` می‌رود. پاسخ مشتری یک نسخه جدید Draft می‌سازد که به نام **مشتری** ثبت می‌شود. Task دوباره باز می‌شود و تغییرات برجسته نمایش داده می‌شود | پرسش، پاسخ و نسخه جدید |
| تأیید | **فقط مسئول احرازشده** | تأیید به `payload_hash` آخرین نسخه Draft و hash پیش‌نمایش (CR-02) گره می‌خورد، با سطح `none`، `confirm` یا `strong` | متن خام، intent تفسیرشده، hash و شاهد تأیید (مثلاً OTP) |
| رد | فقط مسئول | پایان مسیر طبق Workflow. دلیل رد الزامی است | تصمیم و دلیل |
| برگرداندن برای اصلاح | فقط مسئول | در رویداد، نوع تصمیم `returned` همراه با دلیل و هدف (پیش‌فرض: ایجنت قبلی) ارسال می‌شود. n8n پرونده را به گام اصلاح برمی‌گرداند و بعد از اصلاح، Human Task جدیدی ساخته می‌شود | تصمیم و دلیل |
| توقف موقت و ادامه | فقط مسئول (یا نقش مدیر طبق Policy) | `Karyar Case.status = paused`. رویداد `case.paused` منتشر می‌شود. ادامه با `case.resumed` | تصمیم و دلیل |
| لغو پرونده | فقط مسئول (یا نقش مدیر)، با سطح پیش‌فرض `confirm` | `Karyar Case.status = cancelled` (پایانی). رویداد `case.cancelled` منتشر می‌شود. Draft طبق سیاست نگهداری مدیریت می‌شود | تصمیم و دلیل |
| تغییر مسیر | فقط مسئول، **فقط بین مسیرهای مجاز تعریف‌شده** | در رویداد، `route` منتقل می‌شود. Karyar عضویت `route` در `allowed_routes` را بررسی می‌کند | مسیر انتخاب‌شده و دلیل |

**تفاوت «اصلاح داخل Task» و «برگرداندن»:** اصلاح‌های کوچک داخل همان Task و بدون حرکت پرونده انجام می‌شوند. «برگرداندن» یک تصمیم در سطح Workflow است و پرونده را جابه‌جا می‌کند.

## ایجنت فقط پیشنهاددهنده است

- ابزارهای تصمیم‌گیری (`approve`، `reject`، `return`، `pause`، `cancel`، `change_route`) در اختیار ایجنت **نیستند**. ایجنت فقط `task.propose_decision` را دارد.
- تصمیم وقتی ثبت می‌شود که سیستم:
  1. احراز کند فرستنده، مسئولِ همین Task است. هویت از session کاربر می‌آید، نه از متن پیام.
  2. طبق سطح تأیید، خلاصه نهایی را نمایش دهد و تأیید صریح بگیرد.
- **ویرایش‌هایی که ایجنت انجام می‌دهد** به‌صورت «دستور از انسان، اجرا با ایجنت» ثبت می‌شوند. تفاوت قبل و بعد بلافاصله به انسان نشان داده می‌شود. اگر ایجنت دستوری را اشتباه فهمیده باشد، هنگام تأیید نهایی دیده می‌شود، چون خلاصه کامل و hash نمایش داده می‌شوند.
- **پیام‌های مشتری فقط داده‌اند.** هر تغییری که از سمت مشتری بعد از بازبینی انسان بیاید، Task را با برچسب «تغییرکرده پس از بازبینی» علامت می‌زند. تأییدهای قبلی تا بازبینی مجدد نامعتبر می‌شوند.

## پیکربندی برای هر Workflow

یک DocType کوچک به نام **`Human Task Template`** در Karyar تعریف می‌شود. n8n فقط با نام به آن ارجاع می‌دهد: `human_tasks.create(template, case_id, …)`.

| تنظیم | توضیح |
|---|---|
| `assignee_rule` | کاربر مشخص، Frappe Role یا نقش کاری. در صف نقش، Task توسط یک نفر «برداشته» می‌شود (claim) و برای دیگران قفل می‌شود |
| `visible_fields` / `masked_fields` | چه داده‌ای دیده شود |
| `editable_fields` | چه داده‌ای قابل افزودن، ویرایش یا حذف باشد |
| `required_fields` | پیش‌شرط امکان تأیید |
| `allowed_actions` | زیرمجموعه‌ای از اقدام‌های جدول بالا |
| `allowed_routes` | مسیرهای مجاز برای «تغییر مسیر» (مثلاً `doctor_review`، `skip_to_sales`) |
| `confirmation_level` | `none`، `confirm` یا `strong` برای تأیید. برای لغو، پیش‌فرض `confirm` است |
| `re_review_on_change` | بعد از تغییر مشتری یا ایجنت، آیا بازبینی مجدد لازم است |
| `can_ask_customer` | آیا انسان می‌تواند از مشتری اطلاعات بخواهد |

**چرا تنظیمات در Karyar است، نه در n8n؟** محدوده دید و ویرایش و سطح تأیید، **قاعده امنیتی** هستند و باید در Karyar اجرا شوند. n8n هنگام ساخت Task فقط می‌تواند این تنظیمات را **محدودتر** کند، **هرگز گسترده‌تر**. کف ایمنی تأیید در CR-02 هم مستقل از این تنظیمات برقرار است.

## نسخه‌داری داده و ممیزی

- **هر تغییر در Draft یک نسخه جدید می‌سازد.** هر نسخه این‌ها را ثبت می‌کند:
  - شماره نسخه
  - تفاوت در سطح فیلد (مقدار قبل و بعد)
  - hash قبل و بعد
  - منبع تغییر (`human`، `agent_on_behalf_of_human`، `customer` یا `system`)
  - کاربر
  - پیام مرجع
  - زمان
- این نسخه‌ها در همان **`Audit Log` فقط‌افزودنی** با نوع `draft.revised` ثبت می‌شوند. DocType جدیدی لازم نیست.
- **انواع رویداد ممیزی** در Human Task:
  - `task.created`، `task.claimed`، `task.viewed`، `task.message`، `task.tool_call`
  - `draft.revised`
  - `task.customer_info_requested` و `task.customer_info_received`
  - `task.decision_proposed` (توسط ایجنت)
  - `task.decided` (approve، reject، return، route)
  - `case.paused`، `case.resumed`، `case.cancelled`
  - `security.unauthorized_decision_attempt`

## هماهنگی با n8n (CR-01)

- **رویداد تصمیم:** رویداد `human_task.decided` شامل `decision` (approved، rejected، returned)، `route` و `reason` است. n8n روی همین فیلدها مسیر را انتخاب می‌کند (Switch). این یعنی تصمیم انسان، نه منطق داخل n8n.
- **اجرای Pause و Cancel در Karyar:** برای پرونده‌ای با وضعیت `paused` یا `cancelled`، API کاریار همه اقدام‌های کسب‌وکاری و Promote را **رد می‌کند**. حتی اگر یک Workflow در n8n به اجرا ادامه دهد، اثری در ERPNext ندارد. ادامه کار با رویداد `case.resumed` و از مرحله ثبت‌شده در Case انجام می‌شود.
- **«درخواست اطلاعات از مشتری»** داخل Karyar انجام می‌شود و به n8n نیازی ندارد. این قابلیت به CR-01 قاعده ۸ (گفت‌وگوی زنده در Karyar) وابسته است.

## رابط کاربری (Workspace)

صفحه Task دو بخش دارد:

1. **داده ساخت‌یافته:** فیلدها، تغییرات برجسته‌شده بین نسخه‌ها، و پیش‌نمایش ERPNext.
2. **گفت‌وگو با ایجنت.**

دکمه‌ها (تأیید، رد، برگرداندن، توقف، لغو، مسیرها) فقط میانبرهای اختیاری همان اقدام‌ها هستند. در فاز ۱، کارکنان فقط از طریق Workspace کار می‌کنند. انجام Human Task از پیام‌رسان (بله یا تلگرام) برای کارکنان به آینده موکول می‌شود. تأیید `strong` در هر حالت به session احرازشده Workspace نیاز دارد.

## دامنه فاز ۱

| در فاز ۱ | موکول‌شده |
|---|---|
| همه اقدام‌های جدول بالا با **یک مسئول** (کاربر یا صف نقش با claim) | تأیید چندنفره (M از N، ترتیبی یا موازی) |
| `Human Task Template`، نسخه‌داری Draft و ممیزی کامل | انجام Task از پیام‌رسان برای کارکنان |
| Workspace دوبخشی | مهلت و escalation خودکار (فعلاً یادآوری با Cron در n8n) |

## موارد منتظر تأیید در CR-03

1. **تنظیمات Human Task در Karyar باشد** (`Human Task Template`) و n8n فقط بتواند آن را محدودتر کند، نه گسترده‌تر.
2. **لغو پرونده، اسنادی را که قبلاً در ERPNext ثبت شده‌اند خودکار لغو نمی‌کند.** لغو یا اصلاح سند ERPNext یک اقدام جدا و صریح است که سیاست تأیید (CR-02) بر آن اعمال می‌شود.
3. **«درخواست اطلاعات از مشتری»** به CR-01 قاعده ۸ (گفت‌وگوی زنده در Karyar) وابسته است. با تأیید CR-03، پیشنهاد می‌شود قاعده ۸ هم تأییدشده تلقی شود.
